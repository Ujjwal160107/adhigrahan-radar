# Dynamic acquisition-data ingestion — design

**Date:** 2026-09-10 · **Status:** approved · **Closes:** implementation-blueprint risk **X-1**

---

## 1. Why

`data/raw/bhoomirashi/` holds one `.gitkeep`. Every acquisition row in the build is
generated by `s8` from `RISK_SEED`, so every `is_delayed` label is synthetic, so
`n_test_real = 0` for all five stages, so — by the project's own honesty rule 2 — no metric
may be reported as a real-world performance claim. The blueprint calls this "the single
largest risk" and gates Phases 3–6 on it.

This design adds a **source layer** that mirrors real government records into `data/raw/`,
from which the existing pipeline builds a **hybrid corpus**: real rows where the record
exists, synthetic rows to reach trainable volume, every row labelled either way. That is
option **(c)** in the blueprint's risk X-1.

The consumer is the ML work. What it gets is a real label on the one stage whose breach
voids the acquisition.

## 2. What is actually reachable

Verified live on 2026-09-10, not assumed:

| Surface | Access | Carries |
|---|---|---|
| e-Gazette *Search by Ministry* (`SearchMinistry.aspx`) | public, **no CAPTCHA**, ASP.NET ViewState postback | per-notification metadata grid: subject, part/section, issue date, publish date, gazette ID |
| e-Gazette PDF (`WriteReadData/<year>/<id>.pdf`) | public, **no session at all** | the notification text and its schedule of districts, taluks and villages |
| Bhoomi Rashi dropdowns (`filldist1.cshtml`, `fillplace1.cshtml`) | public, **no CAPTCHA** | official state → district → tehsil master data with portal IDs |
| Bhoomi Rashi project search (`search_proj.cshtml`) | public but **dual CAPTCHA** (image + reCAPTCHA) | project-level land required, sanctioned cost, 3a/3A/3D dates |

Three facts shape everything below.

**The gazette ID encodes its own publication date.** `CG-DL-E-30082025-265818` is document
`265818`, published `30-08-2025`. No lookup needed.

**The file number is the project key.** Every notification carries a trailer like
`[F. No 12254/PIU-CHN-II/NH85:Koc-Mun/LA 3a-3A-3D]`, and it is *the same string* on that
project's 3a, 3A and 3D notifications. Grouping by it turns a pile of documents into a
project with dated stage transitions. Without it there is no interval and no label.

**`egazette.gov.in` serves an incomplete TLS chain.** The leaf is signed by Let's Encrypt
intermediate `YR2`, which the server never sends. Stock `curl`, `requests` and `httpx` all
fail with `unable to get local issuer certificate`. The fix is to chase the leaf's
Authority Information Access URL, cache the intermediate, and pin a bundle. The source
layer owns this; nothing works without it.

## 3. Architecture

```
ingest/  ──writes──▶  data/raw/  ──read by──▶  pipeline/  ──▶  vivaad.db  ──▶  backend  ──▶  frontend
   ▲                                              ▲
   │                                              │
 network, on demand                        offline, deterministic,
 (`make ingest`)                           never touches the network
```

`ingest/` is a **source layer, not a pipeline stage** — the same relationship `s0_handoff`
already has to the external `land-cases` corpus. The build never depends on the network;
`make build` on a fresh clone works exactly as it does today.

The dependency arrow is one-way and never reversed. `ingest/` imports nothing from
`pipeline/`. The two communicate only through files in `data/raw/` and `data/input/`.

### Module responsibilities

Each module below has one reason to change. That is the test applied when splitting them.

| Module | Single responsibility |
|---|---|
| `ingest/config.py` | *What* to ingest: target states, source URLs, ministry codes. Pure data, no behaviour. |
| `ingest/http.py` | Get bytes from a URL, politely and reliably: TLS chain repair, retry, rate limit, session. |
| `ingest/cache.py` | Never fetch the same URL twice. |
| `ingest/ledger.py` | Remember which documents exist and what we learned about them, across runs. |
| `ingest/egazette/catalog.py` | Drive the Ministry search and yield metadata rows. |
| `ingest/egazette/documents.py` | Turn a catalog row into document text. |
| `ingest/egazette/parse.py` | Turn document text into a `Notification`. **Pure — no IO.** |
| `ingest/egazette/records.py` | The data contract between the four modules above. |
| `ingest/bhoomirashi/gazetteer.py` | Real state → district → tehsil master data. |
| `ingest/projects.py` | Group notifications into projects with dated stages. **Pure — no IO.** |
| `ingest/refresh.py` | Orchestrate the above. Thin. |

Two modules are deliberately pure functions over plain data (`parse`, `projects`). They
hold all the logic that can be wrong, and they are the two that can be exhaustively tested
without a network.

### Two-stage classification

The metadata grid's `Subject` column is free text and inconsistent — the same August 2025
page carries both `Publication of notification under Section 3D` and `3D Notification`. So:

1. **Filter on metadata, tuned for recall.** A loose subject regex cuts the fetch set from
   every MoRTH notification to plausible land-acquisition ones. A false positive costs one
   PDF fetch; a false negative loses a project.
2. **Classify on document text, authoritatively.** The PDF's own words — *"clause (a) of
   section 3"*, *"section 3A"*, *"sub-section (1) of section 3D"* — decide the section.
   The subject line is a hint and is never trusted.

This is why discovery and parsing are separate modules: they answer different questions with
different confidence.

### Discovery is pluggable; retrieval is not

The Ministry search is ASP.NET WebForms with cookieless sessions, ViewState and
AutoPostBack dropdowns. It works today and it will break eventually. Direct PDF retrieval by
ID needs no session and will not.

So discovery sits behind an interface with a registry of strategies (`ministry_search`
today; a bounded ID walk as a documented fallback). A broken strategy degrades to "no new
rows found" — never to a broken build, because the ledger and the raw cache already hold
everything previously harvested.

## 4. Where this stops

**This work ends at the contract.** `ingest/` writes two files under `data/raw/` and touches
nothing in `pipeline/`, `backend/` or `frontend/`. Wiring the real corpus into `s8`–`s12` is
ML work and belongs to whoever owns the model: how real and synthetic rows are combined, how
missing measures are handled, and what either does to the twenty-feature matrix are modelling
decisions, not ingestion decisions.

The handoff is specified in
[`docs/specs/2026-09-10-acquisition-contract-handoff.md`](2026-09-10-acquisition-contract-handoff.md).

### Target states and districts

The district set is data-driven. `ingest` writes `data/raw/target_districts.json`, ranking
districts by notification count and keeping the top eight per state, with Sultanpur
force-included because the real litigation corpus and the flagship project live there.
Pre-declaring district names would risk selecting eight districts with no notifications in
them.

Bihar is the second state because its `khasra`/`thana-number` vocabulary is the closest of
any state to UP's `khasra`/`gata`, so the existing survey normaliser stays valid without a
new transliteration model; because NH acquisition volume there is high; and because Patna
High Court shares Allahabad's CNR format, so extending litigation coverage later costs no
new code. Madhya Pradesh is the fallback if Bihar's yield is thin.

The harvest itself is **not** limited to those two states. It keeps every §3A and §3D it
parses, whatever the state, because the marginal cost is zero once the document is
downloaded and widening the scope later should not mean re-harvesting. Selecting the target
districts is a filtering step the consumer applies.

### The build's fictional now

`ingest` does **not** filter by `common.TODAY`. Its job is to mirror the source faithfully;
deciding what is in-window is the consumer's. This keeps `TODAY` defined in exactly one place
and keeps the raw mirror a true mirror.

## 5. What becomes real, and what does not

Real, from the gazette:

| Field | Today | After |
|---|---|---|
| `notification_3a_11.is_delayed` | synthetic | **real** — the s.3D(3) 365-day clock, from real 3A and 3D dates |
| `gazette_republication_count` | synthetic | **real** — republished notifications under one file number |
| villages / districts spanned | synthetic | **real** |
| CALA designation | absent | **new, real** |
| `nh_no`, stretch km | synthetic | **real** |

**Only stage 1 gets a real label.** Awards under §3G, compensation disbursement and taking
of possession are never gazetted, so `declaration_3d_19`, `award_3g_23`,
`compensation_disbursed` and `possession` stay synthetic. This is a limit of the public
record, not of the pipeline, and the model registry must state it **per stage** rather than
globally.

That is still the result worth having: `notification_3a_11` is the stage whose breach voids
the notification under s.3D(3), and it is where `n_test_real` goes from 0 to a real number.

## 6. Honesty rules this design must not break

1. Every row keeps a `source_label`. Gazette-derived rows are `real`; generated rows stay
   `synthetic`. They coexist and remain separable by a `WHERE` clause.
2. A metric may be reported per stage only where `n_test_real > 0` **for that stage**.
   Stages 2–5 keep reporting exactly what they report today.
3. The demo never touches the network. `make build` reads `data/raw/`; `make ingest` is a
   separate, explicit, human-run command.
4. The CAPTCHA on Bhoomi Rashi's project search is not circumvented. That path is
   operator-assisted by design, and it is optional enrichment — the labelled spine comes
   from e-Gazette, which has no CAPTCHA.

## 7. Risks

| Risk | Mitigation |
|---|---|
| The ViewState search flow breaks | Discovery is a registry of strategies; the ledger and raw cache preserve prior harvests; the build never depends on discovery succeeding. |
| File numbers are inconsistent across a project's notifications | Normalise before grouping, and report the unmatched rate as a build statistic rather than hiding it. A project whose 3A and 3D cannot be joined contributes no label. |
| Yield is lower than hoped | The corpus stays hybrid. Fewer real rows means a smaller real holdout, reported honestly per stage — not a broken build. |
| PDF layout drift breaks the parser | `parse` is pure and fixture-driven; drift shows up as a failing test on a committed fixture, not as silent data loss. |
| Rate limiting or a block from a `.gov.in` host | Conservative default delay, resumable harvest, on-disk cache so a re-run costs nothing. |

## 8. Out of scope

No live scraping at request time. No CAPTCHA solving. No new matcher — project→parcel
binding continues to use `s2`'s normaliser and gazetteer via `s10`. No change to the REST
contract, the schema, or the frontend.
